# SysWall — Roadmap post-V0.2

> Date : 2026-05-05
> État courant : V0.2 livrée (commits jusqu'à `0488ea8`).
> 6 sous-projets de l'audit du 2026-05-04 livrés, 336 tests verts, 0 clippy warning.

Ce document propose une trajectoire en 4 jalons (V0.3 → V1.0) sur 6-9 mois. Chaque jalon est suffisamment autonome pour être livré indépendamment, et la priorisation reflète le critère « ce qui débloque l'adoption en premier ».

---

## V1.0 — Écosystème & scaling (≈ 8-12 semaines)

**Objectif** : passer de "outil personnel desktop" à "outil sérieux pour pros / petites infras".

### Items

| # | Item | Effort | Priorité |
|---|---|---|---|
| 1.0.1 | **Telemetry anonyme opt-in** : envoyer des stats agrégées (verdicts/jour, top apps bloquées globalement) à un backend SysWall pour piloter les décisions produit. **Strict opt-in**, off par défaut, privacy-first | L | 🟠 |
| 1.0.2 | **Community blocklists** : intégrer URLhaus, OISD, Steven Black hosts via une UI "Subscriptions" qui mette à jour quotidiennement via gRPC | M | 🟠 |
| 1.0.3 | **Application fingerprinting** étendu : au-delà du chemin exe, hash SHA-256 + signature DEB/RPM/Pacman + signature GPG (si binaire signé). L'utilisateur peut créer des règles sur "Firefox signé par Mozilla" plutôt que `/usr/bin/firefox` | L | 🟠 |
| 1.0.4 | **Plugin scripting** via Rhai (Rust embeddable) : règles personnalisées exprimables dans un mini-langage, ex. `if dst_ip in RFC1918 and time.hour > 22 then Allow else Ask` | XL | 🟡 |
| 1.0.5 | **Mode agent / serveur centralisé** : un démon "central" reçoit les flux de plusieurs SysWall agents et permet à un admin de gérer des fleets (TLS mutuel, rotation cert) | XL | 🟡 |

## Stratégie de priorisation

**Pour chaque jalon**, je recommande la séquence :
1. Terminer les items 🔴 (blockers de release).
2. Terminer les items 🟠 (différenciation).
3. Estimer le restant 🟡/🟢 — soit en V0.X.1 patch, soit déférer à V0.X+1.

**Évite de mélanger les jalons** : finir V0.3 entièrement avant d'attaquer V0.4. Chaque jalon a son propre cycle audit (1 jour) → spec (1 jour) → plan (½j) → exec (le reste) → release.

---

## Critères de pivot

Si à un moment ces signaux émergent, je pivote :

- **Plus de 50 utilisateurs sérieux** sur la V0.2 → décaler V0.4 en faveur de V0.5 (packaging) pour absorber la croissance.
- **Bug critique sécurité** trouvé par un utilisateur → V0.X.1 patch immédiat, tout le reste en pause.
- **Dépendance majeure abandonnée** (`nfq`, `aya`, `tonic`) → remplacer en priorité, peut décaler un jalon entier.
- **Nouveau noyau kernel** (≥ 6.10) introduit des features (eBPF KFunc utiles, NFQUEUE async natif) → réévaluer V0.4 / V1.0.

---

## Items hors-roadmap (non prévus)

- **Mode clair (light theme)** : SysWall reste dark-only par design. Si demande utilisateur forte, à reconsidérer en V1.1.
- **Windows/macOS port** : pas dans la mission. SysWall = Linux desktop firewall. Forks équivalents sur autres OS existent (Little Snitch, GlassWire).
- **Mobile (Android)** : hors-scope (Linux desktop uniquement).
- **Cloud/SaaS hosted** : pas dans l'esprit du projet (privacy-first, on-device).

À mon avis, par ordre d'utilité :

1. **V0.3.1** (XS, 30 min) : poser le tag `v0.2.0` et publier la GitHub Release pour rendre la version pushée formellement utilisable. **À faire dès maintenant.**

Le reste peut attendre selon ton bandwidth et tes priorités produit.
